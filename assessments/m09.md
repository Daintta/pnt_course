# Module 09 assessment: PNT Verification, Validation and Assurance

## match
Match each concept to its core question.
- Verification = Did we build the system or requirement correctly?
- Validation = Did we build the right capability for the intended mission and environment?
- Assurance = Is there a justified body of evidence supporting confidence in the critical claims?
> A system can be verified against a poor requirement and still be unsuitable for the mission.

## match
Match each IADT method to a PNT example.
- Inspection = Review the architecture to confirm no undocumented shared antenna path
- Analysis = Predict INS drift or clock holdover against outage duration
- Demonstration = Show a controlled transition from GNSS to alternate navigation
- Test = Remove a source and measure detection, failover, error growth and recovery
> Each method has limitations if used alone; a mature strategy combines them for the strongest evidence.

## single
What is the main limitation of demonstration when used alone?
- It cannot show the implemented system operating.
* It can favour success paths and may not expose boundaries or failure cases.
- It requires reference truth accurate to the millimetre.
- It can only be used for timing systems.
> Demonstration shows capability working, but resilience evidence also needs boundary and failure behaviour.

## single
Which is the most verifiable version of "the system shall detect spoofing"?
- "The system shall be spoof-proof."
- "The system shall use an anti-spoofing receiver."
* "When GNSS becomes inconsistent with the defined independent references beyond the specified threshold, the system shall declare GNSS suspect within the required detection time and prevent it being presented as trusted."
- "The system shall detect spoofing quickly."
> A testable requirement defines the condition, behaviour, response time and threshold.

## single
A receiver is claimed to achieve 10 cm accuracy, but the reference truth used in the trial has an uncertainty of about 8 cm. What is the concern?
- None: any reference is acceptable.
* The claimed performance is close to the reference uncertainty, so the evidence may not support the conclusion.
- The receiver must be more accurate than claimed.
- Reference truth only matters for timing tests.
> The reference must be sufficiently better understood than the system under test, and its uncertainty recorded.

## multi
For a timing holdover test, which aspects of the measurement chain should be characterised?
* Traceability and calibration of the reference clock
* Cable, interface and transfer delays
* The measurement or averaging interval used
* Environmental conditions relevant to the result
- The brand of the laptop used to view results
> A precise-looking measurement is not automatically strong evidence; the measurement chain's uncertainty must be understood.

## match
Match each test environment to its main strength.
- Simulation / recorded data = Repeatable and safe with precise event control
- Laboratory / hardware-in-loop = Controlled, instrumented and reproducible
- Field trial = High operational realism
- Operational exercise = Real users, procedures and system interactions
> Each environment has limitations too. Evidence should combine them and state what is not covered.

## single
Why should nominal performance be established before resilience testing?
- Because nominal performance is the only thing that needs testing.
* Because without a baseline it is hard to distinguish a resilience failure from ordinary system performance.
- Because resilience tests cannot be run without GNSS.
- Because the supplier requires it.
> Nominal performance is the baseline for interpreting behaviour under denial, degradation and deception.

## multi
Which metrics should be measured for detection performance?
* Time to detect / time to alert
* Missed detections and false alarms
* How much erroneous PNT reaches the application before isolation
* Whether the correct integrity and mode state reaches the consumer in time
- The number of satellites in the almanac
> A system that eventually notices a bad source may still fail the mission. Detection must be measured.

## truefalse

= false
> Over-sensitive thresholds cause nuisance alarms and unnecessary failovers; permissive thresholds let hazardous misleading information persist. The balance is mission and risk dependent.

## single
A platform meets its 20 m requirement for 120 s of GNSS loss in straight-line motion but exceeds 20 m after 75 s during aggressive manoeuvres. What should the assurance statement say?
- "GNSS outage resilience passed."
- "The system is unusable."
* The requirement is met only for the tested straight-line dynamics envelope; the requirement or architecture needs refinement for manoeuvring.
- Discard the manoeuvring result as an outlier.
> State what the evidence supports, bounded by configuration, environment, threat condition, duration and performance.

## single
Why is static evaluation needed alongside dynamic testing?
- Static evaluation is faster, so dynamic testing can be skipped.
* A short dynamic test cannot prove that sources are genuinely independent; inspection and analysis can expose shared power, antenna, software, network or supplier dependencies.
- Static evaluation measures position error directly.
- Dynamic tests cannot detect any failures.
> Some claims concern architecture rather than runtime response, so architecture and dependency evidence complements testing.

## single
During a test campaign the final run passes, but an earlier run showed an unexplained mode flip. What should happen to that anomaly?
- Delete it, because the final result passed.
* Record and investigate it: it may reveal a missing requirement, weak monitor, unmodelled dependency or incorrect assumption.
- Rerun until no anomalies appear, then report only the clean run.
- Report it only if the customer asks.
> Do not discard inconvenient anomalies simply because the final test passed.

## multi
Which are recognised assurance anti-patterns?
* Choosing pass/fail criteria after seeing the results
* Testing failover but not recovery
* Treating a simulation result as operational proof without justifying its representativeness
* Treating "certified" as proof for every use case
- Recording the configuration baseline of the system under test
> Recording the configuration baseline is good practice. The others weaken objectivity, coverage or applicability.

## single
What is the value of a PNT assurance case?
- It turns incomplete evidence into certainty.
* It makes claims, evidence, assumptions, limitations and residual risks visible and reviewable.
- It replaces the need for testing.
- It proves a system is resilient in all conditions.
> An assurance case connects a top claim and sub-claims to evidence, assumptions and residual risk; it does not claim absolute resilience.
