# Module 08 assessment: PNT Architecture and Systems Engineering

## order
Put the stages of the top-down PNT systems-engineering flow in order.
1. Mission / user need
2. Use cases
3. PNT dependencies
4. Risks
5. Requirements
6. Architecture
7. Interfaces
8. Verification evidence
> Technology is introduced only after the required capability and tolerances are understood.

## single
A team opens a design meeting with "we need RTK". What is the best systems-engineering response?
- Start the RTK procurement immediately.
* Ask what operational requirement led to that choice.
- Replace RTK with PPP because it is newer.
- Add an INS as well, to be safe.
> Architecture is not the first step. Each technology choice should trace back to a mission need.

## single
Why is "position accuracy shall be 1 m" not yet a good requirement?
- Because 1 m is too accurate for any system.
* Because it lacks operational purpose, coordinate frame, environment, confidence or statistical basis, and the consequence of exceeding it.
- Because accuracy should never be specified.
- Because requirements must name a receiver model.
> A good PNT requirement states what must be achieved under defined conditions, with statistical meaning and consequence.

## single
When turning a user story into operational flows, which flows tend to expose resilience, failover, alerting and recovery requirements?
- The normal success flow only.
* The alternative flows: degraded, misleading-source, extended outage and recovery.
- The flows that describe the user interface layout.
- None; resilience requirements come only from the supplier.
> The normal path often produces performance requirements. The alternative paths expose the resilience requirements that are easily missed.

## truefalse
Drawing the PNT system boundary removes the need to consider dependencies outside it.
= false
> The boundary establishes engineering responsibility, not independence. If failure outside the diagram can invalidate the PNT output, it is still a dependency.

## match
Match each requirement category to an example.
- Functional = Provide UTC-aligned time and a source-health state
- Performance = Accuracy, integrity, availability, continuity, latency and drift
- Resilience = Holdover duration, degraded capability, failover and recovery behaviour
- Interface = Coordinate frame, time scale, units, update rate and status fields
- Support / lifecycle = Calibration, software updates, obsolescence and re-test triggers
> Requirements should cover function, performance, resilience, interfaces, environment, security/assurance and lifecycle.

## single
Why is "accuracy alone is insufficient" when specifying PNT performance?
- Because accuracy cannot be measured.
* Because a one-metre position that is stale, untrusted, in the wrong datum or unavailable at the critical moment may be useless.
- Because integrity is the only attribute that matters.
- Because accuracy is always guaranteed by GNSS.
> Specify the service the mission needs: accuracy, integrity, availability, continuity, latency, update rate, holdover and recovery.

## multi
Which elements belong in a complete resilience requirement statement?
* The critical PNT capability that must survive
* The threat, failure or adverse condition considered
* The performance and duration that must be sustained
* The detection, degraded-mode and recovery behaviour required
- The supplier's marketing tagline
> Resilience is threat-relative and time-bounded, not a Boolean property.

## single
Why must system-level requirements be allocated to architectural functions?
- To make the requirements document longer.
* So that requirements such as "detect misleading PNT" have an architectural owner rather than remaining an aspiration.
- Because allocation replaces verification.
- So that suppliers can choose which requirements to meet.
> Every critical requirement should point to a function that satisfies it, and every critical function should point back to a need or risk.

## match
Match each architecture view to its purpose.
- Functional = What the system must do
- Logical = How functions exchange information
- Physical = Where functions are implemented
- Dependency / assurance = What the system relies on
> One diagram rarely communicates everything. Complementary views reveal different aspects of the same system.

## single
A high-quality PNT subsystem outputs uncertainty and integrity state, but the interface to the application passes only latitude, longitude and time. What is the risk?
- None, because the PNT subsystem is high quality.
* The consumer cannot recognise degraded or untrusted PNT, so an otherwise good subsystem can still create an unsafe system.
- The coordinates will be in the wrong units.
- The interface will run too slowly.
> Many PNT failures become system failures at interfaces. Uncertainty, integrity, freshness and mode information must survive to the consumer.

## single
Which statement best reflects good trade-study discipline?
- "Option A is more resilient."
- Choose the option with the best headline accuracy in ideal conditions.
* Compare options against common mission-derived criteria, record assumptions and evidence, and state which threats and requirements drive the difference.
- Select the most mature technology regardless of requirements.
> Vague conclusions are not traceable. Criteria include performance, resilience, independence, coverage, infrastructure, SWaP-C, integration, maturity, assurance and lifecycle.

## match
Match each anti-pattern to the better question to ask.
- "Dual GNSS = resilient" = Which failures are actually independent?
- "Use INS as backup" = What error is permitted after the required bridging time?
- "Return to normal when GNSS returns" = What revalidation criteria restore trust?
- "Independent timing source" = Is it GNSS-disciplined upstream?
> Anti-patterns look reasonable but hide missing conditions, triggers, durations or dependencies.

## single
What role does a PNT requirements traceability matrix play?
* It links mission need to requirements, architecture allocation, risks and planned verification methods, forming the engineering spine of the design.
- It lists every component's part number.
- It replaces the need for architecture diagrams.
- It is only produced after testing is complete.
> Decide what evidence is needed early: a requirement that cannot be objectively verified is a requirements problem before it is a test problem.

## single
Starting from "the system needs resilient timing because GNSS may be unavailable", what should come first?
- Select a caesium clock.
* Ask what the timing supports and what offset causes the operational service to fail.
- Subscribe to an internet time service.
- Write a test plan.
> The technology choice follows the requirement once the purpose, adverse condition, error bound, duration and recovery needs are defined.
